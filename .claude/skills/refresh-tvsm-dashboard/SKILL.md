# Refresh TVSM Dashboard

Build a validated `index.html` and `data.json` from the latest Tata Steel dumps. Treat coverage stock as shared pools, preserve customer-level demand, and stop publication when hard validation checks fail.

## Daily workflow

1. Retrieve the dumps from whichever mailbox is connected. Tata Steel dumps are forwarded from `apoorv.gupta@tatasteel.com`; they may arrive in the connected Gmail account or in an AgentMail inbox. For AgentMail, list messages then request each attachment, which returns a presigned `download_url` rather than bytes: follow that URL and verify the downloaded size matches the listed attachment size.
2. Select one internally consistent dump set:
   - Use the newest message containing the operational dumps: sales, stock, transfer, YF65, WIP, and RFD.
   - Use the newest RM tracker message containing the TVSM/VSM sheet.
   - Use the latest approved mapping files: the schedule/bucketing/OEM key workbook and `zmat.xlsx`.
   - Do not mix same-category files from different operational dump dates.
   - Check that each dump is actually new before publishing. A file can be re-sent unchanged: compare its content, and read `Ageing days` on the stock extract, whose maximum advances by one per day. A stale stock file publishes yesterday's plant stock, high-age and 8406 cover beside today's sales. When the pack's stock file fails that check, the corrected extract usually follows in its own mail within the hour — as a lone `stock.XLSX` or as the `FG STROCK REPORT` — so build on the freshest stock held, publish, and pick up the correction when it lands rather than waiting.
3. Download attachments into a temporary input directory and rename the required files exactly:

| Canonical filename | Source |
|---|---|
| `rm_tracker_model.xlsx` | The month's schedule sheet, Bucketting, and OEM key mapping workbook. A month-neutral slot: the file that fills it is named for its month (`aug0826 rm tracker v1`) and that name is recorded in `dumps/README.md`, not asserted by the filename |
| `sales.xlsx` | Sales dump |
| `stock.xlsx` | Stock dump. Arrives as `stock.XLSX` or as an `FG STROCK REPORT DD.MM.YYYY.XLSX` under a *FG STOCK SUMMARY* subject; both carry the same `PLANT STOCKS` and `TRANSIT STOCK` sheets and the same 18 columns |
| `wip.xlsx` | WIP/ystockn dump |
| `rfd_4731.xlsx` | 4731 RFD CTL stock dump |
| `zmat.xlsx` | ZMAT material mapping |
| `rm_tracker_tvsm.xlsx` | RM tracker containing the TVSM/VSM sheet |
| `transfer.xlsx` | Inter-plant transfer dump (optional; drives the transfers and STR views) |
| `contract.xlsx` | Customer contract base price sheet (optional; drives the SKU pricing view) |
| `sales_history.xlsx` | Longer sales window in the sales dump's format (optional; widens the code repository) |
| `signoff.xlsx` | Order sign-off by plant, sheets `jsr`, `hosur`, `khopoli` (optional; drives the signed/not-signed columns on the long-length and Megh Steel tabs) |
| `orders.xlsx` | Sales-planning order-book consolidation, sheets `jsr`, `hk_so`, `hk_str` (optional; drives the order columns on the long-length and Megh Steel tabs) |
| `sales_q4.xlsx`, `sales_q1.xlsx`, `sales_<mon>.xlsx` | Archived sales extracts in the sales dump's own layout, `Sheet1` only (optional; drive the past sales trend tab) |

4. Every optional input is used when present and skipped with a warning when absent. Never add transfer movement quantities to the current transit snapshot: transfer drives the transfers view and the STR cover figure only.
5. Run:

```bash
"$CODEX_PRIMARY_RUNTIME_PYTHON" scripts/refresh_dashboard.py \
  --input-dir "<input-directory>" \
  --output-dir "<output-directory>" \
  --as-of "<YYYY-MM-DD>"
```

For a repository checkout, run the command from
`.claude/skills/refresh-tvsm-dashboard`. Copy the approved masters from
`assets/masters/` into the input directory using the canonical filenames
before execution. Install the Python dependencies with:

```bash
"$CODEX_PRIMARY_RUNTIME_PYTHON" -m pip install -r requirements.txt
```

Run the package checks with:

```bash
"$CODEX_PRIMARY_RUNTIME_PYTHON" -m pytest -q tests
```

6. Read `run_summary.json` and `qc_summary.json`.
7. Apply the publication gate:
   - `PASS`: publish.
   - `WARN`: publish with the warning banner and report the mapping gaps.
   - `FAIL`: do not publish. Report the missing inputs or failed checks.
8. Keep `dumps/` to the current month. It holds the latest of every file for the month being published; when a month closes, run `scripts/archive_month.py --month YYYY-MM` to move that set into `dumps/YYYY-MM/`. Trend sources and the two masters stay on top because the pipeline reads them every day; the schedule workbook archives with its month.
9. When publication is requested, update only `index.html`, `data.json` and — when the grant has changed — `access.json` in `apoorvgupta0709/rmtrackerchatgpt` on `main`. Use a commit message such as `Daily TVSM dashboard refresh YYYY-MM-DD`. Refresh `dumps/` with the day's inputs and its `README.md` manifest in the same commit, so the published build can always be reproduced from the repository alone.
10. Never let anything but `index.html`, `data.json` and `access.json` reach the Vercel deployment. The GitHub repository is private; the deployment is not, and serves whatever it receives at a guessable URL with no authentication. `.vercelignore` holds `dumps/` and `.claude/` out of it — `dumps/` above all, which carries sales transactions, receivables ageing and the customer contract prices that no non-admin account is granted.
11. Report the as-of date, status, schedule MT, sales MT, open balance MT, critical/low bucket counts, mapping rates, high-age tonnage at month end, unbacked 4731 CTL tonnage, ancillary overdue, and any warnings.

## Tabs

The dashboard publishes eleven views, in this order: Customer tracker, Megh Steel sales,
Long-length tracker, Missing mappings, Sales summary, Past sales trend, SKU pricing,
Stock analysis, STR to 8406, Transfers, Ancillary overdue. The rules below name a tab rather than
number it, because inserting one renumbers every tab after it.

## Sign-in

The published page opens on a sign-in card and renders nothing behind it until
someone is through — currently `apoorv`, `mes` and `groupbuy` — each checked against a
SHA-256 digest salted with the username so two people sharing a password do not share a
digest. The session is held in `sessionStorage`, survives a reload and ends on sign-out
or when the tab closes.

Grant a meeting account the tabs the meeting argues from, not everything it could read.
`groupbuy`, for the group buy meeting, holds the six commercial tabs — customer tracker,
long-length tracker, sales summary, past sales trend, SKU pricing, stock analysis — and
not the mapping, STR, transfers or overdue queues, which are internal work lists rather
than material for the room. `mes` holds the Megh Steel tracker alone.

`apoorv` is the admin account. It sees every tab plus an Admin tab holding a matrix of
account against tab; ticking a box grants that tab. A non-admin account with no entry
in the grant sees every tab, one with a list sees only that list, and one granted
nothing gets a message saying so rather than a blank page. The admin can preview any
account with “View as”, which hides the Admin tab too so the preview is faithful, and
leave it from the header.

Accounts live in `access.json` too, as `username -> sha256("username:salt:password")`,
so **creating a user is a change to that one file and needs no rebuild.** Use
`scripts/manage_users.py`, which owns the digest and refuses an unknown tab, a
duplicate username or removing the admin:

```bash
python3 scripts/manage_users.py --access access.json list
python3 scripts/manage_users.py --access access.json \
    add <username> --password '<password>' --tabs meghView pricingView
python3 scripts/manage_users.py --access access.json grant <username> --tabs meghView
python3 scripts/manage_users.py --access access.json remove <username>
```

A new account appears in the admin matrix and can sign in as soon as the file is
published. When someone asks for a user to be created, take the username, the password
and the tabs from the list above, run `add`, publish `access.json`, and confirm which
tabs the account will see.

Publish the grant as its own file, `access.json`, beside `index.html` and `data.json`.
A refresh must refresh the tab list inside it — so a newly built tab becomes grantable
— and must never touch the grants, or a daily run would silently reset who sees what.
The admin's edits take effect on their own browser at once through `localStorage`, and
reach anyone else only when the file is published; the panel says so and offers the
file to copy, because a static page cannot write back to its own host.

**Treat this as a name on the door, not access control.** The page is served
statically, so `data.json` can still be fetched directly by URL and the digests reach
the browser like everything else on the page. It keeps the dashboard off a shared
screen and records who is looking; it does not keep anyone out. The same holds for tab
grants: they hide tabs, they do not withhold data, because `data.json` carries every
tab's figures whatever the grant says. Real protection has
to sit in front of the files — a host that authenticates the request, such as Vercel
password protection or an access-controlled deployment — and until that exists, do
not treat publication as private.

## Business rules

- Read `sales.XLSX` → `MATERAIL NUMBER` and `wip ystockn.XLSX` → `Material No` with an explicit string dtype. Both are stored as text, and pandas infers a float dtype that silently drops their last digit, corrupting 90% of sales codes and 89% of WIP codes. No other key column in any dump is affected.
- Normalise every bucket string as it enters from a sheet — trim it, collapse runs of whitespace, and treat a non-breaking space as a space. A bucket is a join key, and a trailing space makes it a *different* string that renders identically, so it silently becomes its own tracker row and its own stock pool. The RM tracker's TVSM sheet wrote `25.4-0-2.5-ERW 1-FC ` on one row: 60.304 MT of TVSM sales sat on a phantom long-length row of their own while the real bucket reported a 56 MT gap it had already dispatched. Apply it to `Bucketting` `Bucket` and `CTL Bucket`, `Schedule July` `Bucket` and `CTL Bucket`, and the RM tracker's `key` on both the `TVSM` and `vsm stock` sheets — everywhere, not only where a sheet has been seen to be dirty.
- Map the material code through `Bucketting` to find the bucket, falling back to the decoded description and physical attributes.
- Group Schedule July demand by `Helper Customer`. Resolve sales OEM through `OEM_key_1_rev codes`; resolve physical buckets through `Bucketting`; use ZMAT to enrich material attributes.
- Recover a schedule line's bucket from `Bucketting` through its `MATERIAL NO` when `Schedule July` leaves `Bucket` or `CTL Bucket` blank. The sheet's own value always wins; this only fills gaps. On the 27 July set it recovers 17.889 MT of Rajsriya Hosur demand that would otherwise reach no bucket and drop out of the long-length and STR views.
- Calculate customer schedule, sales, and balance at customer plus CTL key.
- In the customer tracker, require customer selection and show every SKU with non-zero schedule or dispatch.
- Update the top cards when a customer is selected. Show that customer's schedule MT, sales MT, open-balance MT, unique active SKU count, LL-covered SKU count, and LL-uncovered SKU count. Define an LL-uncovered SKU as a unique active CTL bucket with positive open balance and zero available LL stock. Keep these cards independent of the optional SKU text filter.
- Treat CTL stock as an exact finished-length pool. Only plant 0789 `PLANT STOCKS` CTL rows and mapped `rfd_4731` RFD quantities are valid CTL sources.
- Treat plant LL, mapped `wip ystockn`, and transit rows as one shared bucket-level LL stock pool.
- Resolve WIP buckets from the material code through `Bucketting`, falling back to the description. Reject a code-derived bucket that contradicts the description's own OD, ID and thickness, and leave the row unresolved instead. The WIP dump reuses one code across physically different materials, so a code-derived bucket can drag unrelated sizes into a bucket. Accept a code-derived bucket only when the description's own OD, ID and thickness agree with it, and leave the row unresolved otherwise. Do not apply this guard to `PLANT STOCKS`, whose description formats vary.
- Reconcile 4731 cut length against RFD on weight and on quantity, never on presence. A material can appear in RFD and still be overstated in SAP, so state how much RFD backs, in MT, and how much has to be written off; sum the gaps for the write-off total rather than whole unbacked lines. Where one RFD line names several SAP codes, share its weight between them in proportion to what SAP holds so the same stock cannot back two materials, and say so in the comment.
- Never compare the `NOS` column at 4731 or 8406 to a piece count. SAP holds those two locations in kilograms only and repeats `KG` in `NOS` on every row, so a piece-for-piece comparison is kilograms against units and reports a material as half short when it is backed in full. Publish no piece count for those plants rather than a number that reads as pieces; 0789 and 0788 carry genuine counts and are unaffected.
- Do not treat `rfd_4731` `CTL Code` as a reliable key. It is blank on a quarter of the rows carrying stock, and where populated it may hold several codes separated by slashes or a free-text note, so keyed on the raw cell those rows back nothing and a material physically at the plant is told to write itself off. Split the cell on `/`, `|` or `,`, keep the numeric entries, take the first that `Bucketting` governs, and carry every listed code so one RFD line can back several SAP materials.
- Where no code resolves, identify the row by its own size: OD, ID, thickness and cut length, matched against the 4731 cut-length materials `PLANT STOCKS` holds, reading OD, ID and thickness out of each SAP description. A rectangular row puts its two outer dimensions in `Section` and leaves `OD` holding the equivalent round diameter, so read `Section` for those and never `OD`; a round row has no second dimension, which is zero on both sides. Where several SAP codes share a size, back all of them, and take the recovered bucket into the pool only when those codes agree on one. Report the rows that still reach no bucket, with the reason each failed, rather than assuming them.
- Report bucket mapping coverage per inventory source on the stock analysis tab — rows, total MT, mapped MT, unmapped MT and unmapped % for `PLANT STOCKS`, WIP ystockn and RFD 4731 — and make the unmapped tonnage open its line items. A global resolution rate hides which source is failing and where to fix it. State that `Bucketting` governs the TVS range, so material held for other customers maps at a lower rate by design, and name the holder on each drill-down line so that is visible. Queue each source's unmapped rows in the missing-mappings tab in its own table, with an assign-to-bucket control wherever a governed bucket is the fix.
- Never build a CTL bucket from a missing bucket. A NaN is truthy in Python, so guarding on truthiness alone yields the string `"nan-0.46"`, which passes bucket validation, counts as resolved and matches nothing — the stock silently leaves circulation while resolution reads 100%. Test for NaN explicitly and let the unresolved count report the gap.
- Classify a stock row as long length when the `CTL/LL` flag is `LL` or the length is at least 3.5 m, and as CTL only when the flag is `CTL` and the length is below 3.5 m. Rows carrying a length range in the description leave `LENGTH` at 0, so neither signal is sufficient alone.
- Attribute stock held by customer 943209 (`MEGH STEELS PRIVATE LIMITED - TVS A`) to the TVS pool. The OEM key classifies it as `Direct`, so without an explicit override its long-length stock is invisible to TVS schedule rows. Keep this pool attribution separate from the sales-by-OEM classification.
- Provide a clearance-list copy on the customer tracker, written to be pasted into WhatsApp rather than a spreadsheet: no tabs, short lines, `*bold*` and `_italic_` markers, numbered SKUs with the size, the material code and the quantity in nos. Cover cut length only, in nos, and only where the pool holds more than 500 nos — below that there is nothing worth asking clearance for. Deduplicate on CTL bucket first: CTL stock is a shared pool and one customer can carry the same bucket on more than one row, so listing it twice offers the same pieces twice and double counts the total. Write dimensions without thousand separators, because "1,130 mm" reads as a quantity on a phone, and drop a placeholder material code such as `NO MATERIAL CODE` rather than quoting it back to the customer.
- Provide a dispatch-plan copy on the customer tracker. For the selected customer, emit one tab-separated line per SKU with open balance, ordered by OD, thickness and cut length, under a `DATE : DD.MM.YYYY` and customer heading, with columns PLANT, ACTUAL OD, OD, ID, THICKNESS, CTL, NOS, MT, SO and a closing total MT row. Take the SO from the most recent earlier invoice, resolving in order of specificity: same customer and material code, same customer and CTL bucket, same material code, same CTL bucket. A sales order is customer-specific, so never quote another customer's order where that customer's own exists. Leave it blank when no earlier invoice exists rather than quoting an unrelated order. Quote a numeric plant code, taken from the matched invoice's supply plant, learning the location-to-code mapping from matched lines for the rest.
- Show a subtotal row directly beneath the header of every table, pinned so it stays visible while scrolling, giving the sum of whatever the active filters leave on screen. Sum only columns whose total is meaningful, and sum the unrounded values rather than the displayed text so the figure does not drift across hundreds of rows. Never total the shared CTL and LL pool columns, which carry `do_not_sum` semantics, nor day counts such as coverage days, stock age or days overdue.
- Give every tab's table, and the drill-down modal, a copy button that copies the table as tab-separated text for spreadsheet paste, with numeric cells stripped of grouping separators and unit suffixes.
- Display CTL stock as a NOS button and LL stock as an MT button. Each button must open stock details with source/plant, SKU, material code, quantity, and unit.
- Display shared CTL and LL pools with `do_not_sum` semantics. Never repeat and sum the same pool across customer rows.
- Treat the transfer dump as movement history only; never add its quantities to stock.
- Read stock from the `PLANT STOCKS` sheet only; never read the `TRANSIT STOCK` sheet, which holds the same batches and would double count. Include `PLANT STOCKS` rows whose customer is `TRANSIT STOCK` in available stock as a shared bucket-level pool, alongside WIP, and remove them from the owned CTL/LL pools so the tonnage is not counted twice. Show these rows as source `Transit` with their `PLANT STOCKS` plant.
- Use `RFD Qty.` from mapped `rfd_4731` rows as plant 4731 CTL stock. Do not also add 4731 CTL rows from `PLANT STOCKS`.
- Classify long-length coverage: `<15` days Critical, `15–<30` Low, `30–<45` Watch, `>=45` Adequate.
- Sort the long-length tracker by ascending natural bucket order.
- The LL tracker has seven metric columns: total schedule, total sales, total stock, order logged, coverage days, balance, and gap to 45 days. Balance is schedule less sales, netted per stream then added. Each is a button with source/formula breakup.
- Compute the balance by netting each demand stream against its own sales, then adding: TVS gap is `Schedule July` TVS schedule minus TVS sales, VSM gap is the RM tracker TVSM sheet's `VSM Requirement` minus `VSM Sales`, and the total gap is their sum. Floor each component at zero before adding so over-dispatch on one stream cannot mask a real gap on the other.
- Consolidate plant LL stock, mapped WIP ystockn, transit stock, and TVSM stock into one total-stock button; retain source/plant/material detail in its drill-down.
- Read the order book from `orders.xlsx`, one sheet per despatching origin, and take each sheet's own open-quantity column: `jsr` (Jamshedpur, sales and STRs) on `Bal to Desp`, `hk_so` (Hosur and Khopoli sales to Megh Steel and TVSM) on `BAL FOR PROD/ROLL(MT)`, and `hk_str` (Hosur and Khopoli STRs to the stock yards) on `Actual BTP (MT)`. The three report different stages of the same commitment — left to despatch, left to produce, booked to production — so never substitute one column for another or add them as if they were the same measure. `hk_so` puts its header on the second row; `hk_str` carries no material number at all, so its bucket comes from the description alone. Translate the planning sheets' `PT-HOUS`, `PT-KHP` and `PT-JSR` to the SAP plant numbers 789, 788 and 56 the rest of the dashboard uses.
- Carry each line's order age in days, taken from whichever column that sheet states it in: `AGE` on `jsr`, `Ageing Days` on `hk_so`. `hk_str` states no age at all, only `STR Date`, the date the STR was raised, so derive its age as the as-of date less that date — quoting the raised date where a day count belongs would read as an eleven-year-old order. Show the age on every order drill-down line.
- Exclude every order line the planners have marked `c` in the sheet's remarks column — `Remarks` on `jsr` and `hk_so`, `REMARKS` on `hk_str`. Those lines are not live demand and must reach neither tracker's pool. Report what was excluded per origin beside what survived, because the mark carries 59% of the 31 July book and an order column that quietly halved would be read as a collapse in demand rather than as a filter. Every rate and total on the order book is computed on the live lines only.
- Show the pooled order book as an **Order logged** column on the long-length tracker, keyed on the governed bucket, opening the line items behind it plant by plant with origin, order number, customer, material code, description, the basis each quantity is open on and the line's age in days. Keep it out of coverage days and the gap columns: an order is demand already committed, not stock, and folding it into cover would overstate what is available.
- Show Megh Steel's own orders on the Megh Steel tab as **Orders logged as per sales planning**, keyed on the VSM SKU, beside — never instead of — the `vsm stock` plan's figure, which is renamed **Orders logged as per OMS**. The two sources disagree, and seeing both is the point.
- List the excluded lines on the missing-mappings tab too, so the sheet accounts for every line in the book — labelled *Excluded on purpose*, sorted last, and filterable out. They are not a gap to close, so they stay out of the unmapped counts, and the actionable rows lead.
- List **every** order line absent from a view that should carry it individually in its own missing-mappings table — one row per line, with plant, type, order number, customer, material code, description, the bucket and SKU it did or did not reach, the line's age and its tonnage. Name the cause on each: no governed bucket; the bucket carries no schedule so the long-length tracker has no row; the bucket does not govern the line's length so no VSM SKU key exists; or the SKU is absent from the `vsm stock` plan. A line missing from both views carries both labels rather than appearing twice, so the tonnage total is the whole gap with nothing double counted. On the 30 July book that is 119 lines and 2,194.555 MT of a 15,556.840 MT order book — enough that a single pooled figure would read as the whole book when it is not.
- State on every one of those rows **which view it is missing from and which view it is still visible on**, and lead the table with the rows visible on neither. Absence from a view is not the same as an unmapped material: a Megh order on an unscheduled bucket shows on the Megh Steel tab with its full tonnage and is absent only from the long-length tracker, where nothing is wrong with the order at all — the tracker's rows are the buckets carrying a schedule. Listed without that distinction on a tab headed *Missing mappings*, such a row reads as a mapping failure and sends someone to fix a mapping that is already correct. On the 30 July book 1,010.496 MT of the 2,194.555 MT is visible on no view; the rest is visible on one.
- Megh Steel runs a **vendor service model**: Tata Steel supplies Megh Steel, and Megh Steel supplies TVSM, Royal Enfield and HMSIL. The `vsm stock` plan covers all three, so the tab is not a TVSM-only view and must not be read as one.
- Read the `vsm stock` `key` column as **two** shapes, told apart by the `Megh-` prefix. Without it the key is a governed TVS bucket, `OD-ID-thickness-grade-endcondition`. With it the size is one Megh Steel supplies onward to **RE or HMSIL** rather than TVSM, written `Megh-OD-ID-thickness-length` — the same five parts, where the last two mean thickness and length rather than grade and end condition. Parsing one as the other builds a SKU key out of the word `Megh` and reads a cut type off a length. The prefix says which OEM the size is for; it does not say the size is ungoverned, and a prefixed size having no TVS bucket is the expected state rather than a gap, so keep those rows out of the assign-a-bucket and add-the-code-to-`Bucketting` queues.
- Name the end OEM on every row and let the tab be sliced by it. The prefix does not distinguish RE from HMSIL, so read that from the conversion-agent code that has bought the size — 943210 is HMSIL, 943211 is RE — over the whole sales window the trend files supply rather than the current month alone, so a size last sold in April is still attributed. A prefixed size no code has bought yet reads *RE or HMSIL* and answers to both filters, which is honest about what is known. On the 31 July plan: 69 TVSM, 7 HMSIL, 3 RE and 14 undetermined.
- Use the plan's own per-plant material codes as a second route from stock, sales and WIP to a Megh SKU, applied where the bucket join found nothing. A Megh-only size has no governed bucket, so the bucket join can never reach it: on the 31 July plan those 22 codes carry 183.923 MT of stock and 181.434 MT of sales that are otherwise invisible. Take the bucket route first and the code route only as a fallback, so a governed size keeps the key every other frame agrees on.
- Build the Megh SKU key from the `vsm stock` sheet's governed `key` column plus its `Length`, never from its own `O D`, `Thk.`, `Grade` or `FC/NFC` cells. The two disagree on thickness grouping, on rectangular sections written as an equivalent round OD, on grade qualifiers, on cut type and on rounding — so a dimension-built key puts the plan on one key and stock, sales and WIP on another, and the SKU shows no mapped stock while the same material sits in the long-length tracker. Keep the dimension build as a fallback: 38 of the 94 tracked rows carry no key because Bucketting does not govern their size, mostly the 1.4 mm range, and those legitimately map to no stock. Derive the cut token inside the key from the bucket's end condition so both sides agree, but label the SKU from the plan's own `FC/NFC` column — `FC` is fin cut, `NFC` is not — which is the better answer where a bucket ends in something that says nothing about finning, such as `CEW`. The key is a join, not a description, so the two may differ.
- Publish a Megh Steel SKU tab after the customer tracker, driven by the RM tracker's `vsm stock` sheet. Use only rows carrying a non-zero schedule or stock. Key each SKU as `OD-ID-thickness-length-grade-cut type`, where cut type is `FC` when `FC/NFC` is fin cut and `NFC` otherwise.
- Source the tab's columns as follows, and give every quantity a breakup:
  - schedule, ground stock, in-transit stock and orders logged from the `vsm stock` sheet. Its quantities are kilograms — `Stock` reconciles to `NOS x Wt/Len` and its own `Coverage` equals `Stock / Schedule x 30` — so divide by 1000 for MT. Orders logged is the sum of the per-plant `... Order` columns, not `Order qty to be logged`, which is the residual still to raise.
  - sales to Megh from the sales dump for customer codes 943209, 943210 and 943211.
  - stock at the required length and at other lengths from `PLANT STOCKS` plus `wip ystockn`, restricted to long length. A cut piece cannot be re-cut to a Megh SKU.
- Flag the bought-out parts on the Megh Steel tab with a **BOP** column and a filter that slices the table four ways — BOP and converted, BOP only, converted only, BOP sizes not in the plan — composing with the existing cut-type, end-OEM and search filters. A BOP item is a size Megh buys finished rather than converting. The list is governed in `MEGH_BOP_ITEMS` as dimensions, a nominal length, pieces and plant, exactly as supplied. Match a listed line to the SKU whose bucket agrees on dimension one, dimension two and thickness — that keys a rectangular section such as 40 x 25 as written, where matching on OD would not — then take the nearest length. Assign nearest-first and claim each listed line and each SKU once: 19.05 x 2.0 is listed twice, at 5840 and 6000, and letting each line take its own nearest hands 5.841 to both and leaves 5.8 unflagged.
- Match a BOP length only within **50 mm**. The band has to stay inside a cut-length rounding: at 200 mm it pulled 19.05 x 2.0 x 6000 onto the plan's 5.8 m row, and the owner's ruling is that a gap that size is a different item. Say when a match was made on a nearest length rather than an equal one, with the gap in millimetres.
- **A listed BOP size the plan has no row for becomes its own line item on the tab**, marked `in_plan: false` with an *off plan* badge. Megh buys the size whether or not `vsm stock` names it. Leave every plan-fed column at zero — schedule, stock, both order columns, sales — and still join the long-length columns for real, since what long length is available to cut it from is the question the row exists to answer. Take grade and cut type from the plan's own rows of the same diameter and thickness when they agree and write `lookup error` when they do not. Name the added sizes under the table so the note reads as *the plan is short of this size*, never as a matching failure.
- Read the customer-code-to-OEM mapping across the whole sales history, not the daily dump alone. A code's OEM does not change month to month, but the daily dump only covers the month in progress: on 3 August it held three days and 125 lines, most schedule customers had not bought yet, and schedule OEM resolution fell to 66.75% against the 99% gate — a FAIL produced by the calendar, not the data.
- Take each trend month from exactly one source, the daily dump first and the archives filling the rest. **Archive a month's sales dump as the month closes**, adding it to `SALES_TREND_FILES`: the daily dump stops covering a month the moment the next begins, and July existed in no quarterly extract, so on 1 August the trend silently lost 3,344.836 MT — the most recent complete month. The one-month-one-source rule is what makes archiving safe while the dump still covers it.
- **The schedule sheet's name is a slot, not a month.** The August master still calls it `Schedule July` while carrying August demand, so the month it covers is declared by `SCHEDULE_MONTH` and the two move independently. Set `SCHEDULE_MONTH` when a new month's workbook arrives; the mismatch banner keys off it.
- **Not every customer's schedule reaches the master.** In August 8 of 18 were typed into it and the other 10 arrived as their own mails — spreadsheets in ten different layouts, a PDF, and two whose table is only in the mail body. Prepare those into `schedule_supplement.xlsx` with the schedule sheet's own columns; the pipeline appends it and the master's zero rows drop out, so a customer in both is counted once.
- Build a supplement row by finding the customer's existing row for that size and writing the quantity into a copy of it — never by re-deriving the bucket. The sheet already holds every one of those customers' sizes with its governed bucket, CTL bucket and material code; only the quantity is blank. Match on the sheet's `OD`/`ID` columns, not `ACTUAL OD`, which holds the equivalent round diameter for a rectangular section, and normalise both sides through `norm_od`/`norm_thickness` so a customer writing 1.22 meets the governed 1.2.
- Where a customer states no bore, accept a match on OD, wall and length **only if it lands on one row**; two rows differing only by bore are two different tubes. Where a size is new this month, take its bucket from `Bucketting` only when exactly one candidate exists, and otherwise leave it unmapped so it reaches the Missing mappings tab with a readable description. A guessed bucket pools demand onto a size nobody ordered.
- Weigh a supplement row by the customer's own stated MT, and leave the cell blank otherwise so the pipeline's governed formula computes it. **Never read a weight out of `Bucketting.kG/nos`**: the column is kilograms per piece on a cut-length row and kilograms per metre on a 5.6 m or 6 m one, and there is nothing in the row to say which. The formula agrees with the trustworthy rows to 0.05%.
- Fold a near-value dimension onto the governed one through `OD_GROUPS` and `THICKNESS_GROUPS` rather than treating it as a new size. Check first that `Bucketting` really does hold one value and nothing near it — 22.23 and never 22.2, 41.28 and never 41.3, 1.2 and never 1.21 or 1.22, 1.6 and never 1.62 or 1.63.
- Give the schedule gaps their own table on the Missing mappings tab, beside the Megh, WIP, stock, RFD and order queues, with a copy button and a `Schedule` value on the type filter. They also appear in the tab's first table, but that table reads as being about materials and customers, so a queue that only lives there cannot be found. Every row must name its size as the customer wrote it — a row showing `lookup error` for the size names nothing and is a defect.
- Show orders on the long-length and Megh Steel tabs as **two columns, signed off and not signed off**, rather than one total: a signed-off order is firm demand a SKU has to be covered against and the rest is not yet, and a single figure cannot answer either question. Each opens a drill-down giving both halves per plant and material code.
- Read each `signoff.xlsx` sheet on its own terms — they share only the material code. `jsr` marks sign-off with a Y/N flag, so a line's whole `Bal to Desp` falls to one side; `hosur` states the signed MT and the rest of `Order Qty in MT` is unsigned; `khopoli` states both halves outright and its `Order Qty in MT` is pieces despite the name. Ignore `jsr`'s `Sign Off Qty`: it exceeds the balance on 9 of 27 rows, so it measures something else. Clamp a derived remainder at zero, or a sheet signing off more than it ordered lends the difference back.
- Name any sign-off material code that reaches neither a governed bucket nor a plan SKU on the Missing mappings tab. Its tonnage is in the file and on no tracker row.
- Never key Megh SKUs on `ctl_bucket`: it collapses every length at or above 3.5 m to a single LL marker, while Megh buys specific lengths. Match on the VSM key throughout, never on the sales material number.
- Publish a **Megh length-bucketing** below the Megh SKU table and export it as `megh_length_bucketing.csv`. Megh Steel buys length-specific sizes, so its governing mapping is the bucket *plus* the length, and `Bucketting` alone cannot supply it: the plan's own `056`/`0789`/`0788` columns name material codes `Bucketting` has never heard of. Build one row per length-specific SKU with its bucket, dimensions, grade, cut type, the plan's material codes and the plants that hold them, which of those codes `Bucketting` governs, and the schedule — then resolve an order or sale through it whenever `Bucketting` has no row for the code. Code 4149395 is the case that requires it: the plan governs it as `25.4-0-1.6-ERW 1-FC` at 5.84 m, `Bucketting` holds no row at all, so the SKU showed on the Megh tab while an order for the same code reached no bucket and was reported as unmapped. Flag the codes `Bucketting` lacks as the queue to clear, and treat a non-numeric entry such as `NEW MCR` as a note that a code is still to be created, never as a code.
- Normalise the plan's mixed length units before anything keys on them. `vsm stock` states most lengths in metres and a few in millimetres — 650, 780 and 572.5 sit beside 5.84 and 6.0 in the same column — so treat a value above 20 as millimetres and divide it down. No tube in this business is 20 m. Left alone a 650 mm cut piece keys as 650 m, classifies as long length and matches no stock at all.
- Emit `megh_sku_mapping.csv` as a worksheet for the owner to complete, and keep it beside the dumps. Include the plan rows that reach no SKU key at all, identified by their dimensions — one 48.6 x 1.6 x 572.5 mm row carries 20 MT of schedule with its key, grade and `FC/NFC` cells all empty, so it appears on no tab and in no mapping, which is precisely a size that needs assigning rather than dropping. State on each row which of four things is missing — the bucket, a material code, the code's `Bucketting` entry, or the plan's key/grade/cut type — put the rows needing work first by descending schedule, and leave the assignment columns blank rather than asking for the answer to be written over what the pipeline derived.
- Test every plan cell for NaN explicitly. NaN is truthy, so `if not sku` lets a keyless row through to become a mapping key, and `bucket or None` keeps a NaN as the bucket, which then reads as governed and never reaches the assign-a-bucket queue — the same trap as the `"nan-0.46"` CTL buckets.
- Recover a material code from the description through `zmat` where a sheet states none — the stock-transfer sheet states a description only. Resolve in this order: the sheet's own code column, then the `zmat` description, then the Megh length-bucketing. Where a description is extended under several codes, recover none — naming one arbitrarily could raise a transfer on the wrong material — and quote the candidates so the blank is explained.
- Treat `zmat.xlsx` as the **only** material master. When an extract arrives covering descriptions it lacks, merge it in with `scripts/merge_material_mapping.py` and discard the extract; never keep it beside `zmat` as a second source to filter and reason about on every run, and never store it in the repository. Merging appends **only descriptions `zmat` lacks**: an extract lists several codes per description, so filtering it on the code instead gives a description `zmat` already resolved a second code, and every line that resolved through that description loses its code. Align the extract's columns **by name**, never by position — the two files hold the same columns in a different order, so a positional rename transposes the file, writing descriptions into the code column and plants into the material type. Refuse the merge if any column is still unmatched. After merging, copy the file to every `zmat.xlsx` in the repository and update the checksum in `config/master_manifest.json`.
- Show a value the pipeline looked up and could not resolve as **`lookup error`**, on the page and in the exports alike, rather than leaving the cell empty. An empty cell reads as "nothing to report" and gets skimmed past; the whole point of these queues is that the empty cells are the work. Colour it as a failure, not greyed out as an absence, and let it copy as the words so a pasted sheet carries the same signal.
- Test for NaN explicitly wherever a recovered code decides a label. A missing code arrives as NaN, which is truthy, so guarding on truthiness alone reports a blank cell as a code the sheet stated and a line with no recovery at all as one `zmat` supplied.
- List every Megh sales material that reaches no VSM SKU in its own table on the missing-mappings tab, showing the key derived from the material beside a dropdown of every SKU so the material can be assigned and the result copied back to the source mapping. Assignments are a session-local working aid and are never written back.
- Make every table's header sortable ascending and descending on click, sorting numeric columns on their exact value rather than their formatted text.
- Drop the WIP dump's trailing plant-subtotal and grand-total rows before anything else. They carry no material code and each repeats the file's entire tonnage, trebling apparent WIP.
- List WIP that resolves to no bucket in its own table on the missing-mappings tab, with the tonnage, batch count, why it failed, the bucket its material code claimed, and a dropdown of every governed bucket so it can be assigned and copied back into `Bucketting`.
- Publish a Missing mappings tab with the exception queues:
  - missing material mappings only for sales whose `OEM_key_1_rev codes` OEM is `TVS`, plus all sales for customer code `943209`;
  - every sales customer code/name absent from `OEM_key_1_rev codes`, evaluated before any Boiler material-group override.
- Publish a Sales summary tab summarizing sales by OEM using `OEM_key_1_rev codes`.
- Publish a Stock analysis tab: physical `PLANT STOCKS` tonnage as material line items, in two tables for cut length and long length, each ordered by descending stock age. Group by plant, material and the customer the stock is held for, and show plant, material code, description, held-for customer, oldest age, stock MT, high-age MT, stock NOS and batch count. The customer makes high-age stock actionable by showing who it can be liquidated to. Each MT figure is a button opening its batch-level detail with batch, ageing date, age in days and age at month end. This is an inventory view of the whole sheet, deliberately wider than the approved coverage sources used by the customer and long-length trackers.
- Flag every 4731 cut-length line with its RFD position and total the unbacked tonnage in `qc_summary.json`, per the reconciliation rules above. Split it across four columns rather than one sentence: a verdict — Match, Short in RFD, Not in RFD, RFD holds more — the tonnage RFD matches, the tonnage it does not, and the sentence explaining the difference. Colour only a real shortfall as a failure; RFD holding more than SAP is worth seeing but is not tonnage to write off.
- Make the matched and unmatched tonnage add back to the row's own stock, so both columns can be totalled. The reconciliation is per material and a stock row is per material and holder, so allocate a material's matched and unmatched tonnage across its rows in proportion to what each holds — repeating the material total on every row doubles it in the subtotal the moment one code is held for two customers. Scope the columns to plant 4731: the same code is stocked elsewhere, and keying on the material alone gives an 0789 row 4731's verdict and scales its tonnage by 4731's SAP total. The flag is bookkeeping only; coverage already uses RFD quantity for 4731 CTL.
- Offer both a plant filter and a cut-length/long-length filter above the stock tables.
- Report high-age stock alongside it, defined as ageing over 60 days **at month end**: carry each row's `Ageing days` forward from the as-of date to the last day of that month before applying the threshold, so a mid-month refresh reports the month-end position rather than understating it.
- Report open payments and credit notes as one column beside the overdue, opening a document-level breakup. They are not invoices to chase, so they stay out of the overdue total, but they offset what is owed and must not be discarded.
- Split CRFH line items into their own table below the customer tracker for Marathwada and Sri Balaji Gear, which buy a large CRFH range alongside their tube SKUs.
- Show the selected customer's **sales history** on the customer tracker, both as a per-line column opening a month-by-month drill-down and as a table under the tracker listing every SKU that customer has bought over the trend window — including SKUs carrying no schedule this month, which is the half a buying meeting cannot get anywhere else. Mark each history row against this month's schedule and offer a scope filter: every SKU bought, on this month's schedule only, bought before but not scheduled now. Average over the months a SKU actually moved, not over the window, because an occasional large order and a small steady one are bought differently.
- Join that history on the SAP codes the tracker customer itself names, never on the customer name and never through `display_by_code`. The two sides write a customer's name differently, so a name join is a guess; `display_by_code` drops any code used under more than one Helper Customer, which is right for moving stock and wrong for showing history — three codes are shared on the 31 July build, and routing through it emptied the table for two real customers across 45 lines. Where a code is shared, show the history under both names and say which other customer it is shared with. Where a customer has none, state the cause — no sales under its codes, or no code recorded — because a blank table reads as "bought nothing".

Count only billing documents, doc types `RV` and `RD`, which are exactly the rows whose `Nature` is `BILLING`; debit balances, credit notes and collections are not invoices to chase. Show `Billing Doc` as the invoice number, not `Document Number`, which is the accounting document. Apply this to customers whose OEM resolves to TVS. Treat `yf65.xlsx` as optional so a dump set without it still publishes.

STRs run from 0789, 0788 and 4731 into 8406, and the plan holds 15 days of forward cover at 8406 for Neel Metal, Rajsriya Hosur, Rajsriya Mysore, Sandhar Hosur and Sandhar Mysore. Daily rate is the bucket's schedule MT for those customers divided by the days in the as-of month. Cover is stock at 8406 earmarked to them plus everything in transit to 8406; the requirement is `max(0, 15 x daily - cover)`. Show bucket, the cut lengths scheduled against it in millimetres, schedule MT, sales MT, the 15-day requirement, cover and the requirement, then sending-plant stock as one column per plant — 0789, 0788 and 4731 separately, because an STR is raised on a single plant and a combined figure cannot be acted on. Bridge `Helper Customer` to the stock dump's SAP customer name through the sales dump's code/name pairs, dropping any code the schedule uses under more than one Helper Customer. List stock at 8406 held for customers outside the plan, and state the tonnage of plan lines that carry no `Bucket` in `Schedule July`.
- Allocate the requirement across what the sending plants hold and offer that allocation as the STR placement list: source plant, destination 8406, finished-goods code, description, bucket, quantity and remark. Offer long lengths before cut lengths and finished goods before mother tubes, largest holding first inside each, and close a bucket the plants cannot cover with an explicit shortfall line rather than dropping it.
- Transfer a WIP mother tube under a finished-goods code, never its own. `PTM-` material is semi-finished and not orderable; the finished goods booked against it carry the same description under `TUB-`, so swap the prefix and look the description up in `zmat` restricted to `MATERIAL TYPE = FERT`. A description is extended under several codes, so prefer one extended to the despatching plant, then one whose governed bucket matches, then the lowest code. - Publish a SKU pricing tab that prices every scheduled SKU off the customer contract in `contract.xlsx`. Join the contract's `Key` — dimension1-dimension2-thickness, the second dimension empty for a round tube — to the first three parts of the governed `Bucket`, comparing the dimensions numerically and treating an empty or zero second dimension as zero. A drawn CEW bucket names its bore where the contract names nothing, so retry such a bucket against the round key, but only when `dim1 - 2 x thickness` is within 0.6 mm of `dim2`. Read the three most recent contract quarters. Quote a long length in INR per metre and a cut length in INR per piece at its own length. Never subtotal a price column: the table mixes both units.
- Take value adds from the sheet that governs each: fin cut at 250 when `Schedule July` `FC/NFC` is `FC` or `FIN CUT`, chamferring at 700 from its own column, angle cut at 200 when `Angle Cut` is `AG`, and annealing at 1000 for ERW or 1250 for CEW when `Bucketting` marks the material `AN` or its description carries an `-AN-` segment. - Maintain a repository of every bill-to, ship-to, plant and material code combination actually billed to a TVS customer or a Megh Steel conversion code. One customer buys the same SKU under several material codes, the same code ships from several plants, and bill-to differs from ship-to, so a price change raised on the SKU or the sold-to party alone misses combinations. Read `sales_history.xlsx` when it is supplied, since the daily dump is the current month only and a code last billed earlier would be missing; leave the rest of the dashboard on the daily dump, whose sales are month-to-date by definition.

A code billed but never scheduled carries no contract price — emit the line with an empty price and say so in the basis rather than dropping it, because a silently short request is worse than a visibly incomplete one.
- Let the filter popup's value list scroll. It is a flex column, and a flex item defaults to `min-height: auto` and so refuses to shrink below its content: without an explicit `min-height: 0` the list grows past the popup instead of scrolling, and a column with many distinct values has no scrollbar to drag at all. Keep the popup wholly on screen — clamp both edges, not just the right, and drop it above its header when there is no room below.

[config/master_manifest.json](config/master_manifest.json) as the repository
